
整个过程分为两大阶段：Server层，存储引擎层


相同的操作：
第一阶段：Server 层（连接管理与查询处理）
1. 连接器 (Connector)
作用：负责与客户端建立连接、获取权限、维持和管理连接。

过程：

客户端使用 TCP 连接或命名管道等方式连接到 MySQL 服务器。

连接器验证你的用户名和密码。

验证通过后，连接器会到权限表（mysql.user等）中查出你拥有的权限。之后，这个连接里的权限判断逻辑，都依赖于此时读到的权限，这意味着一个连接一旦建立，即使管理员修改了该用户的权限，也不会影响已经存在的连接的权限。

连接成功后，连接器会进入空闲状态，等待客户端发送 SQL 语句。如果长时间（由 wait_timeout控制，默认 8 小时）没有动作，连接器会自动断开连接。

3. 分析器 (Analyzer)

词法分析 (Lexical Analysis)：

识别 SQL 字符串中的关键字，如 SELECT, FROM, WHERE, my_table, id等。

判断输入的 SQL 语句是否符合 MySQL 的语法规范。例如，将 my_table识别为“表名”，id识别为“列名”。

语法分析 (Syntax Analysis)：

根据词法分析的结果，进一步判断 SQL 语句的语法是否正确。

如果你的语句不对，比如写成 SELCT * FROM my_table，分析器会抛出错误：You have an error in your SQL syntax...。

4. 优化器 (Optimizer)
作用：这是 MySQL 查询性能优化的核心。当分析器生成了正确的语法树后，优化器会决定如何最高效地执行这条 SQL 语句。

优化内容：

多表关联 (JOIN) 时，决定各个表的连接顺序。例如，A JOIN B，是用 A 驱动 B，还是用 B 驱动 A？不同的顺序效率可能天差地别。

选择合适的索引。即使你在 WHERE条件中有多个可用的索引，或者一个联合索引，优化器需要决定使用哪一个。

决定是否进行全表扫描。有时优化器认为全表扫描比走索引更快（例如在表数据量很小，或索引选择性很差的情况下）。

对 ORDER BY, GROUP BY子句的处理。可能会利用索引来避免昂贵的文件排序 (filesort)。

最终产物：优化器会生成一个执行计划 (Execution Plan)。你可以使用 EXPLAIN命令来查看这个计划，它是我们进行 SQL 调优最重要的依据。

5. 执行器 (Executor)
作用：根据优化器生成的执行计划，调用存储引擎的接口，一步一步地执行查询，并最终返回结果。

过程：

权限检查：在开始执行前，还会做一次权限校验。因为查询缓存命中的情况不会经过分析器，所以执行器这里需要再次确认是否有操作目标表的权限。

打开表：根据表的引擎类型，打开相应的表。

调用存储引擎 API：

执行器会根据执行计划中确定的访问方法（例如通过主键索引、二级索引、全表扫描等）来逐行读取数据。

例如，如果执行计划是使用 id > 10的条件通过主键索引查找，执行器就会调用存储引擎的 index_read(...)或 index_range_read(...)等接口。

存储引擎负责找到符合条件的行，并将其返回给执行器。

处理 WHERE 条件：执行器会拿着从存储引擎取回来的每一行数据，按照 WHERE子句中的条件进行过滤。如果不符合条件，就丢弃；如果符合条件，则暂存起来（如果是全表扫描，可能会用到临时表）。

处理其他操作：如果查询有 GROUP BY, HAVING, ORDER BY, LIMIT等操作，执行器会在内存或磁盘上完成这些计算。

返回结果：将最终结果集返回给客户端。对于有 LIMIT的查询，会在此时截断结果集。


Update
第二阶段：InnoDB 存储引擎层（核心修改与日志记录）
这是 UPDATE过程最核心、最复杂的部分。我们假设 autocommit=1（默认自动提交），并且使用的是 InnoDB 引擎。

步骤 1: 定位数据并加锁
执行器调用 InnoDB 的读接口，根据优化器选择的执行计划，找到需要更新的行。

在读取数据的同时，InnoDB 会为这些行加上行级排他锁 (X Lock)。如果 WHERE 条件无法使用索引，导致全表扫描，则会对扫描到的所有行加锁（最终可能会升级为表锁），这就是所谓的“间隙锁”或“Next-Key Lock”，用于防止幻读。

此时，其他事务如果试图修改或加锁这些行，会被阻塞。

步骤 2: 写 Undo Log（回滚日志）
在真正修改内存中的数据之前，InnoDB 会先将这行数据的旧版本（修改前的样子）拷贝到 Undo Log​ 中。

作用：

实现事务回滚：如果当前事务需要回滚，InnoDB 可以利用 Undo Log 中的信息将数据恢复到修改前的状态。

实现 MVCC (多版本并发控制)：当一个旧事务仍在运行时，新事务可以看到数据的旧版本。这个旧版本就是通过 Undo Log 链构建出来的。这使得读操作不会被写操作阻塞。

步骤 3: 更新内存数据
InnoDB 将 Buffer Pool（缓冲池）中对应数据页的该行数据进行修改。此时，内存中的数据已经是新值，但磁盘上的数据页还是旧值。

这时，内存中的页被称为“脏页”（Dirty Page），因为它与磁盘上的数据不一致。

步骤 4: 写 Redo Log（重做日志） - Prepare 阶段
在数据页被修改后，InnoDB 会将这次修改的物理操作（例如：“在表空间 X，页 Y，偏移量 Z 的地方写入了值 A”）记录到 Redo Log Buffer​ 中，并最终将其刷新到磁盘的 Redo Log 文件​ 中。

关键点：此时 Redo Log 记录的状态是 PREPARE（准备）​ 状态。

作用：Redo Log 是保证事务持久性 (Durability)​ 的关键。它遵循 WAL (Write-Ahead Logging)​ 原则，即“日志先行”。即使在数据页还未刷回磁盘时发生崩溃，重启后也能通过 Redo Log 重做这些修改，从而恢复数据。注意：此时事务并未提交。

至此，InnoDB 层的第一阶段工作完成，它通知 Server 层的执行器：“我这边数据已经准备好，日志也写好了（处于 PREPARE 状态）。”

第三阶段：Server 层与 InnoDB 协作（两阶段提交 - 2PC）
为了保证 Redo Log 和 Binlog 这两个重要日志的一致性，MySQL 使用了两阶段提交 (Two-Phase Commit, 2PC)​ 协议。这是分布式事务的经典思想，在这里被用于保证单个数据库内部日志的一致性。

步骤 5: 写 Binlog（归档日志）
执行器接收到 InnoDB 的准备完成信号后，开始将此次 UPDATE的逻辑操作（SQL 语句本身或由参数构成的逻辑事件）写入到 Binlog (Binary Log)​ 中。

Binlog 是 Server 层的日志，所有存储引擎都可以使用。它的主要作用是主从复制和按时间点恢复数据 (Point-in-Time Recovery, PITR)。

执行器会将 Binlog 写入 Binlog Cache，并在某个时机（取决于 sync_binlog参数）将其刷盘。

步骤 6 & 7: 提交事务与 Redo Log Commit
步骤 6: 提交事务

执行器写完 Binlog 并成功刷盘后，会向 InnoDB 发出一个“提交”请求。

步骤 7: 写 Redo Log (Commit 状态)

InnoDB 收到提交请求后，会将之前处于 PREPARE状态的 Redo Log 记录标记为 COMMIT状态，并将其刷盘（或至少保证该提交标记持久化）。

至此，整个事务才算是正式提交成功。

为什么需要两阶段提交？

想象一下，如果没有两阶段提交，可能会出现以下问题：

场景：一个 UPDATE操作，刚写完 Redo Log（Prepare），还没写 Binlog，系统就崩溃了。

恢复时：InnoDB 发现有一个 Prepare 状态的 Redo Log，但没有对应的 Binlog。它会判定这个事务未完成，从而回滚它。这看起来没问题。

场景：一个 UPDATE操作，Redo Log 已经 Prepare，然后 Binlog 写完了，但在 Redo Log 标记为 Commit 之前崩溃了。

恢复时：InnoDB 发现有一个 Prepare 状态的 Redo Log，并且去检查 Binlog。如果它在 Binlog 中找到了这个事务的完整记录，说明 Binlog 已经完整写入。InnoDB 会重做 (REDO)​ 这个事务（即使数据页没刷盘，靠 Redo Log 也能恢复），并将 Redo Log 标记为 Commit。

反之，如果在 Binlog 中找不到这个事务的记录，InnoDB 就会回滚它。

结论：两阶段提交确保了 Redo Log 和 Binlog 要么同时有效，要么同时无效，从而保证了主库和从库数据的一致性。

第四阶段：后续收尾工作
释放锁：事务提交成功后，之前在步骤 1 中获取的行锁会被释放。

后台刷脏页：InnoDB 的后台线程会在合适的时机（如 Buffer Pool 不足、Redo Log 写满时）将 Buffer Pool 中的脏页刷新到磁盘数据文件中。这个操作与用户事务是异步的，不影响事务的响应时间。

返回结果：执行器向客户端返回成功信息（如 “Query OK, 1 row affected”）。


DELETE
第二阶段：InnoDB 存储引擎层（核心标记与日志记录）
假设使用 InnoDB 引擎且 autocommit=1。

步骤 1: 定位数据并加锁
执行器调用 InnoDB 的读接口，根据执行计划查找需要删除的行。

与 UPDATE一样，InnoDB 会在读取数据的同时，为这些行加上行级排他锁 (X Lock)。如果 WHERE条件不走索引，会导致全表扫描并对所有扫描到的行加锁，这会严重影响并发性能。

步骤 2: 写 Undo Log（回滚日志）
在修改数据之前，InnoDB 会将要删除的这整行数据的完整旧版本拷贝到 Undo Log​ 中。

作用：

事务回滚：如果事务回滚，InnoDB 可以利用 Undo Log 中的完整记录将数据完整地恢复回来。

实现 MVCC：这是 DELETE操作中 Undo Log 最关键的作用。被删除的行并不会立即消失，而是通过一种叫做“隐藏字段”（如 DB_TRX_ID和 DB_ROLL_PTR）的机制，在 Undo Log 中形成一个旧版本链表。正在运行的其他事务，如果其隔离级别允许（如 Read Committed 或 Repeatable Read），仍然可以通过这个链表访问到被删除行的历史版本，仿佛它没有被删除一样。这就保证了读操作不会被写操作阻塞。

步骤 3: 标记删除（更新内存数据）
这是 DELETE操作与 UPDATE在操作上的一个细微差别。InnoDB 并不会直接从数据页中物理擦除这一行。

相反，它会在 Buffer Pool 中将这行数据中一个名为 DELETED的隐藏标记位（实际上是通过更新事务ID等信息来逻辑表示）设置为“已删除”状态。

同时，这行数据所占用的空间变得“可复用”，但数据本身依然留在原地，直到被后续的 Purge线程清理。

此时，内存中的数据页也变成了“脏页”。

步骤 4: 写 Redo Log（重做日志） - Prepare 阶段
和 UPDATE完全一样，InnoDB 会将这次“标记删除”的操作（一个物理或逻辑操作）记录到 Redo Log 中，并将其状态设置为 PREPARE。

这遵循 WAL (Write-Ahead Logging) 原则，确保在崩溃后能够恢复这次删除操作（即恢复那个“已删除”的标记）。

此时，InnoDB 通知 Server 层准备阶段已完成。

第三阶段：两阶段提交 (2PC)
为了保证 Redo Log 和 Binlog 的一致性，DELETE同样采用两阶段提交流程。

步骤 5: 写 Binlog（归档日志）
执行器收到 InnoDB 的 PREPARE信号后，将 DELETE语句的逻辑操作写入 Binlog。

Binlog 中记录的是“删除某张表某行的逻辑事件”。

步骤 6 & 7: 提交事务与 Redo Log Commit
步骤 6: 执行器写完 Binlog 并刷盘后，向 InnoDB 发出提交请求。

步骤 7: InnoDB 收到请求后，将 Redo Log 的状态从 PREPARE改为 COMMIT并刷盘。事务正式提交成功。

两阶段提交的意义：与 UPDATE完全相同，它确保了主库的 Redo Log 和 Binlog 在任何一个时刻都不会出现“一个提交成功，另一个失败”的不一致状态，从而保证了主从复制的数据一致性。

第四阶段：后续收尾工作（Purge 线程）
这是 DELETE过程一个非常重要的后续步骤，也是它与 UPDATE在物理表现上一个关键的不同点。

立即返回结果：事务提交成功后，执行器立即向客户端返回“成功删除 N 行”的信息。此时，对用户来说，删除操作已经完成。

释放锁：事务提交后，步骤 1 中获取的行锁被释放。

异步 Purge（清理）：

被标记为“已删除”的行并不会立即从磁盘上物理删除。它们仍然占用着数据页的空间。

InnoDB 有一个独立的后台线程，叫做 Purge Thread（清理线程）。这个线程的工作就是专门负责清理这些不再需要的 Undo Log 记录和已经被逻辑删除的行数据。

Purge 线程会定期检查，当确定没有任何活跃的事务再需要访问这些被删除行的历史版本时（即没有比创建 Undo Log 更早的活跃事务），它才会真正地从数据页中物理地擦除这些数据，并回收它们占用的空间。

这个清理过程是异步的，所以一个大批量 DELETE操作可能会导致表的实际空间（.ibd 文件大小）在一段时间内不会缩小，因为只是做了标记，而没有立即归还给操作系统。

INSERT
第二阶段：InnoDB 存储引擎层（核心写入与日志记录）
假设我们使用 InnoDB 引擎，并且 autocommit=1。

步骤 1: 检查约束与缓存自增ID
在执行器准备好数据后，InnoDB 首先要进行一系列检查：

外键约束检查：如果表有外键，并且插入的值引用了另一张表的主键，InnoDB 会去检查被引用的表中是否存在对应的值。

数据类型和长度检查：确保插入的值与列定义的类型和长度匹配。

唯一性约束检查：这是最关键的一步。InnoDB 会检查插入的数据是否会违反 UNIQUE索引或主键的唯一性约束。为了高效地检查，它会尝试在对应的索引 B+Tree 中查找，看是否已经存在相同的键值。

自增主键 (AUTO_INCREMENT) 处理：如果表有自增主键，InnoDB 会从内存结构（自增计数器）中获取下一个可用的 ID 值分配给新行。这个值是被缓存起来的，以提高性能，所以 SHOW TABLE STATUS看到的 Auto_increment值可能比实际插入的最大值要大。

步骤 2 & 3: 写 Undo Log（回滚日志）
与 UPDATE和 DELETE一样，在修改数据之前，InnoDB 会先将这行数据的旧版本信息写入 Undo Log。

但对于 INSERT来说，“旧版本”的概念比较特殊：因为这行数据是全新的，不存在于表中。所以，Undo Log 中记录的实际上是如何“撤销”这次插入的信息。

具体来说，它会记录新插入行的主键（或唯一标识）。当事务回滚时，InnoDB 可以根据这个信息，在表中快速定位到刚刚插入的行并将其物理删除。

作用：

事务回滚：使 ROLLBACK成为可能。

实现 MVCC：对于其他并发事务，如果它们的快照是在当前事务提交之前建立的，它们应该“看不到”这个新插入的行。InnoDB 通过将这个“插入”操作记录在 Undo Log 中，使得这些老事务在遍历索引时，可以排除掉这个尚未提交的插入版本。

步骤 4: 更新内存数据与分配事务ID
InnoDB 将这行新的数据插入到 Buffer Pool（缓冲池）中对应的数据页里。如果该数据页还不在内存中，则会先从磁盘加载进来，再进行插入。

同时，InnoDB 会为这行数据分配一个事务ID (TRX_ID)，这个 ID 记录了是哪个事务插入了这行数据。这个 ID 被存储在行的隐藏字段中，是 MVCC 实现的关键。

此时，内存中的数据页又变成了一个“脏页”。

步骤 5: 写 Redo Log（重做日志） - Prepare 阶段
InnoDB 会将这次“插入一行数据”的物理操作（例如：“在表空间 X，页 Y，位置 Z 插入了一行数据”）记录到 Redo Log Buffer，并根据 innodb_flush_log_at_trx_commit的设置，将其刷新到磁盘的 Redo Log 文件中。

和 UPDATE/DELETE一样，此时的 Redo Log 记录状态是 PREPARE（准备）​ 状态。

此时，InnoDB 通知 Server 层的执行器准备阶段已完成。

第三阶段：两阶段提交 (2PC)
为了保证 Redo Log 和 Binlog 的一致性，INSERT也必须走两阶段提交流程。

步骤 6: 写 Binlog（归档日志）
执行器收到 InnoDB 的 PREPARE信号后，开始将此次 INSERT的逻辑操作（即 INSERT INTO ... VALUES ...语句本身或等效的逻辑事件）写入到 Binlog​ 中，并刷盘。

步骤 7 & 8: 提交事务与 Redo Log Commit
步骤 7: 执行器写完 Binlog 后，向 InnoDB 发出“提交”请求。

步骤 8: InnoDB 收到请求后，将之前处于 PREPARE状态的 Redo Log 记录标记为 COMMIT状态，并将其持久化。事务正式提交成功。

两阶段提交的意义：与 UPDATE/DELETE完全相同。它确保了在主库崩溃恢复时，不会出现一个日志认为事务提交了，而另一个日志认为没提交的情况，从而保证了主从复制的正确性。

第四阶段：后续收尾工作
释放资源：事务提交成功后，相关的锁（如果有，例如插入意向锁）会被释放。

异步刷脏页：InnoDB 的后台线程会在合适的时机将包含新数据的脏页刷新到磁盘的数据文件中。

返回结果：执行器向客户端返回成功信息（如 “Query OK, 1 row affected”）。

特殊情况：INSERT ... ON DUPLICATE KEY UPDATE
当使用这个语句时，过程会变得有趣：

InnoDB 首先会像普通 INSERT一样，尝试插入新行。

在步骤 1 检查唯一性约束时，如果发现冲突（违反了主键或唯一索引），它就不会继续插入，而是转而执行一个 UPDATE操作。

后续的流程就变成了 UPDATE的流程：它会写一条 UPDATE相关的 Undo Log，修改内存中的数据，并记录 Redo Log (Prepare)，然后继续执行两阶段提交。
